    The Lens: Functions as First-Class Citizens¶

    In Python, functions are first-class objects. This is a core design principle with profound implications for how we structure code. It means that a function can be treated like any other piece of data: it can be assigned to a variable, passed as an argument to another function, returned as a result from a function, and stored in data structures like lists or dictionaries. This paradigm elevates functions from mere executable blocks to versatile tools for abstraction and composition.

    This capability is the foundation for a style of programming known as functional programming, which emphasizes pure functions, immutability, and the avoidance of side effects. For the computational economist, these patterns are not mere academic curiosities; they are practical tools for building modular, testable, and maintainable models. For instance, a complex economic model can be composed of smaller, independent functions representing utility, production, and policy rules. These components can be swapped, tested in isolation, and reused across different models, leading to more robust and flexible research code.

    This chapter explores these advanced patterns, moving beyond basic function definition to cover the tools that unlock the full potential of functions in Python:

    • First-Class Functions: The core concept of treating functions as data.
    • Higher-Order Functions: Functions that accept other functions as arguments or return them as results (the Strategy Pattern).
    • Anonymous lambda Functions: Creating small, one-off functions.
    • Closures and the nonlocal keyword: Functions that carry their enclosing environment with them, enabling function factories.
    • Callable Classes (__call__): An alternative, object-oriented way to create stateful function-like objects.
    • Decorators: A clean syntax for applying higher-order functions, including decorators that take arguments and the powerful built-in @lru_cache.
    • Generic Functions: Using single dispatch to create functions that adapt to different data types.
    • functools.partial: A tool for creating specialized functions by pre-filling some arguments.

    Learning Objectives¶

    • Write functions with default arguments, *args, **kwargs, and type hints.
    • Use closures, decorators, and functools for reusable abstractions.
    • Apply lambda functions and map/filter for concise data transformations.

    Higher-Order Functions: The Strategy Pattern¶

    A higher-order function is a function that operates on other functions, either by taking them as arguments or by returning them. The ability to pass a function as an argument allows for the implementation of the Strategy Pattern, a design pattern where the specific algorithm used by a function can be selected at runtime by passing in a different "strategy" function.

    Economic Application: Imagine you have a model that can be solved using different numerical methods (e.g., bisection, Newton's method) or evaluated using different utility functions (e.g., CRRA, CARA). Instead of writing a large if/elif/else block to select the method, you can write a single solve function that accepts the chosen solution algorithm as an argument. This makes the code cleaner, more modular, and easier to extend with new solution methods without modifying the solve function itself.

    def crra_utility(c: float, *, gamma: float) -> float:
    """Calculates Constant Relative Risk Aversion utility."""
    if not c > 0:
        raise ValueError("Consumption must be positive.")
    if gamma == 1:
        return math.log(c)
    return (c ** (1 - gamma)) / (1 - gamma)


def cara_utility(c: float, *, eta: float) -> float:
    """Calculates Constant Absolute Risk Aversion utility."""
    if not eta > 0:
        raise ValueError("Risk aversion coefficient eta must be positive.")
    return (1 - math.exp(-eta * c)) / eta


# A registry mapping names to function objects. This is the core of the pattern.
UTILITY_FUNCTIONS = {"crra": crra_utility, "cara": cara_utility}


def evaluate_policy(
    consumption_path: List[float], utility_func: Callable, params: Dict
) -> float:
    """A higher-order function that evaluates a policy by applying a selected utility function."""
    # The chosen utility function is called inside the list comprehension.
    total_utility = sum(utility_func(c, **params) for c in consumption_path)
    return total_utility


path = [10, 11, 12]
crra_params = {"gamma": 2.0}
cara_params = {"eta": 0.5}

print("Evaluating the same policy with different utility function strategies:")
u1 = evaluate_policy(path, UTILITY_FUNCTIONS["crra"], crra_params)
u2 = evaluate_policy(path, UTILITY_FUNCTIONS["cara"], cara_params)

print(f"Total CRRA utility (gamma=2.0) over path {path}: {u1:.3f}")
print(f"Total CARA utility (eta=0.5) over path {path}:   {u2:.3f}")

    Anonymous lambda Functions and the operator Module¶

    While def is the standard way to create a function, Python also provides the lambda keyword for creating small, anonymous functions. These are syntactically restricted to a single expression and are often used when you need a simple, one-off function for a short period.

    Syntax: lambda arguments: expression

    The expression's result is implicitly returned. Lambdas are most commonly found as arguments to higher-order functions like sorted(), map(), or filter(). While convenient, they should be used sparingly. If the logic is complex or the function is used in multiple places, a named function using def is almost always better for readability and debugging.

    For the common case of creating a key function that simply accesses an attribute or item, the operator module provides attrgetter and itemgetter. These are generally more efficient and more readable than an equivalent lambda.

    models = [
    {"name": "Solow", "complexity": 3, "year": 1956},
    {"name": "RBC", "complexity": 7, "year": 1982},
    {"name": "HANK", "complexity": 9, "year": 2018},
]

print("Sorting models by complexity using a lambda function as the key:")
# The key argument expects a function that takes one item and returns a sorting key.
# A lambda is a concise way to provide this function inline.
models_sorted_by_complexity = sorted(models, key=lambda model: model["complexity"])
for model in models_sorted_by_complexity:
    print(f"  - {model['name']} (Complexity: {model['complexity']})")

print(
    "\nSorting models by year using operator.itemgetter (more efficient and readable):"
)
models_sorted_by_year = sorted(models, key=operator.itemgetter("year"))
for model in models_sorted_by_year:
    print(f"  - {model['name']} (Year: {model['year']})")

    Closures and the nonlocal Keyword¶

    A closure is an inner function that remembers and has access to the variables from its enclosing lexical scope, even after the outer function has finished executing. The inner function "closes over" these free variables (variables that are not local to the inner function but are from its enclosing scope). This mechanism is fundamental to functional programming patterns in Python.

    As the diagram illustrates, when the outer function (make_cobb_douglas) is called, the inner function (production_function) is created. The inner function maintains a reference to the alpha variable from its parent scope in its __closure__ attribute. When the outer function finishes and its local scope is destroyed, the alpha variable lives on, kept alive by the closure. This is a powerful concept for creating function factories: higher-order functions that generate and return new, specialized functions based on their inputs. The factory takes the configuration parameters, and the returned function is a clean, simple callable that has those parameters "baked in".

    The nonlocal keyword allows the inner function to modify a free variable from the enclosing scope. Without it, assigning to a variable inside the inner function would create a new local variable, shadowing the outer one.

    def make_cobb_douglas(alpha: float) -> Callable[[float, float], float]:
    """A factory that creates a Cobb-Douglas production function with a specific alpha."""
    # `alpha` is a free variable for the `production_function` closure.
    if not 0 < alpha < 1:
        raise ValueError("alpha must be between 0 and 1.")

    def production_function(K: float, L: float) -> float:
        """Calculates output Y = K**alpha * L**(1-alpha)."""
        return (K**alpha) * (L ** (1 - alpha))

    return production_function


print("Creating two different production functions from the factory:")
# us_prod_func has alpha=0.33 'baked in'
us_prod_func = make_cobb_douglas(0.33)
# eu_prod_func has alpha=0.30 'baked in'
eu_prod_func = make_cobb_douglas(0.30)

K, L = 100, 200  # Capital and Labor
print(f"US-calibrated output (alpha=0.33) with K={K}, L={L}: {us_prod_func(K, L):.2f}")
print(f"EU-calibrated output (alpha=0.30) with K={K}, L={L}: {eu_prod_func(K, L):.2f}")

    def make_counter():
    """A factory that creates a simple counter function."""
    count = 0  # This is the free variable

    def counter():
        nonlocal count  # Declare that we are modifying the 'count' from the outer scope
        count += 1
        return count

    return counter


counter_a = make_counter()
counter_b = make_counter()

print("Each counter function has its own independent state stored in its closure.")
print(f"Counter A, call 1: {counter_a()}")
print(f"Counter A, call 2: {counter_a()}")
print(f"Counter B, call 1: {counter_b()}")
print(f"Counter A, call 3: {counter_a()}")

    Callable Classes: An Object-Oriented Alternative to Closures¶

    Another way to create a stateful, function-like object is to create a class that implements the __call__ special method. This allows an instance of the class to be called as if it were a function. The object's state can be stored as instance attributes (e.g., self.count, self.total).

    Closures vs. Callable Classes: - Closures are often lighter-weight and more concise for simple cases where you just need to store a few pieces of state. - Callable Classes are better when the state is more complex or when you need multiple methods to interact with that state. They provide a more formal, structured approach that is familiar to object-oriented programmers.

    class RunningAverager:
    def __init__(self):
        self.count = 0
        self.total = 0.0

    def __call__(self, new_value: float) -> float:
        """This method makes instances of the class callable."""
        self.count += 1
        self.total += new_value
        return self.total / self.count


print("The callable instance maintains its internal state across calls:")
avg_instance = RunningAverager()
print(f"Average after adding 10: {avg_instance(10):.2f}")
print(f"Average after adding 20: {avg_instance(20):.2f}")
print(f"Average after adding 3:  {avg_instance(3):.2f}")

    Decorators: Syntactic Sugar for Function Wrapping¶

    A decorator is a higher-order function that takes another function as an argument, adds some functionality to it (without modifying the original function's code), and returns the new, enhanced function. The @ syntax is syntactic sugar that makes this pattern clean and readable.

    As the diagram shows, the @my_decorator syntax is exactly equivalent to defining my_func and then immediately reassigning the name my_func to the result of calling my_decorator(my_func). The decorator consumes the original function and replaces it with a new, wrapped version.

    Decorators are ideal for handling cross-cutting concerns—aspects of a program that affect many other parts of the system, such as logging, timing, caching, or authentication. They allow you to separate this boilerplate logic from the core business logic of your functions.

    A well-behaved decorator uses @functools.wraps on its inner wrapper function. This is crucial as it copies the metadata (like the name __name__ and docstring __doc__) from the original function to the wrapped function, which is essential for introspection and debugging.

    def retry(max_attempts: int, delay: float) -> Callable:
    """Factory for a decorator that retries a function if it raises an exception."""

    def decorator(func: Callable) -> Callable:
        @wraps(func)
        def wrapper(*args, **kwargs):
            attempts = 0
            while attempts < max_attempts:
                try:
                    return func(*args, **kwargs)  # Attempt to run the function
                except Exception as e:
                    attempts += 1
                    if attempts >= max_attempts:
                        print(
                            f"Function {func.__name__!r} failed after {max_attempts} attempts."
                        )
                        raise  # Re-raise the final exception
                    else:
                        print(
                            f"Attempt {attempts} failed: {e}. Retrying in {delay}s..."
                        )
                        time.sleep(delay)

        return wrapper

    return decorator


FAIL_COUNT = 0


@retry(max_attempts=3, delay=0.1)
def fetch_data_from_flaky_api():
    """Simulates fetching data from an API that might fail temporarily."""
    global FAIL_COUNT
    print("  Attempting to fetch data...")
    if FAIL_COUNT < 2:
        FAIL_COUNT += 1
        raise IOError("Network timeout")
    return {"data": "some important economic data"}


print("Calling the decorated function that fails twice before succeeding:")
data = fetch_data_from_flaky_api()
print(f"Successfully retrieved data: {data}")

    Memoization from Scratch¶

    Before using the built-in tool, let's build a memoization decorator to understand how it works. It uses a closure (a dictionary cache) to store results.

    def memoize(func):
    cache = {}
    @wraps(func)
    def wrapper(*args):
        if args not in cache:
            cache[args] = func(*args)
        return cache[args]
    return wrapper

@memoize
def factorial(n):
    return 1 if n == 0 else n * factorial(n - 1)

print(f"Factorial of 5: {factorial(5)}")

    @lru_cache: A Powerful Built-in Decorator for Dynamic Programming¶

    A classic application of decorators is memoization: caching the results of expensive function calls and returning the cached result when the same inputs occur again. This is particularly powerful for optimizing recursive functions with overlapping subproblems, a hallmark of dynamic programming.

    The standard library's @functools.lru_cache provides a robust, production-ready implementation of this pattern. It implements a **L**east **R**ecently **U**sed cache: when the cache is full, it discards the item that hasn't been accessed for the longest time. The maxsize argument controls the cache size; setting maxsize=None allows the cache to grow indefinitely.

    Warning: Use @lru_cache only on pure functions whose output depends solely on their inputs. It should not be used on functions with side effects (e.g., modifying a global variable, writing to a file) or functions that depend on external state.

    def fib_naive(n):
    if n < 2:
        return n
    return fib_naive(n - 2) + fib_naive(n - 1)


@lru_cache(maxsize=None)  # maxsize=None means the cache can grow indefinitely
def fib_cached(n):
    """A cached version of the Fibonacci function."""
    if n < 2:
        return n
    return fib_cached(n - 2) + fib_cached(n - 1)


N = 35
print(f"Calculating fib({N}) with the cached version...")
start_time = time.perf_counter()
result_cached = fib_cached(N)
time_cached = time.perf_counter() - start_time
print(f"  Result: {result_cached:,}, Time: {time_cached:.6f}s")
print(f"  Cache info: {fib_cached.cache_info()}")

print(f"\nCalculating fib({N}) with the naive, uncached version (will be slow)...")
start_time = time.perf_counter()
result_naive = fib_naive(N)
time_naive = time.perf_counter() - start_time
print(f"  Result: {result_naive:,}, Time: {time_naive:.6f}s")

if time_cached > 0 and time_cached < time_naive:
    print(
        f"> **Note:** The cached version was approximately {time_naive / time_cached:,.0f}x faster."
    )

    Generic Functions with Single Dispatch¶

    A common problem is wanting a function to behave differently based on the type of its first argument. The traditional approach is a messy if/isinstance chain. A much cleaner, more extensible solution is to use generic functions, a concept from multiple dispatch. While Python doesn't support full multiple dispatch, the @functools.singledispatch decorator allows dispatching based on the type of the first argument.

    You define the base function for the default case, and then use the .register() attribute of the new generic function (which acts as a decorator itself) to provide specialized implementations for specific types.

    @singledispatch
def summarize(data: Any) -> str:
    """The base/default implementation for our generic function."""
    return f"Unstructured data of type {type(data).__name__}"

@summarize.register(dict)
def _(data: dict) -> str:
    """A specialized implementation for dictionaries."""
    keys = ", ".join(data.keys())
    return f"A dictionary with {len(data)} keys: {keys}"

@summarize.register(pd.DataFrame)
def _(data: pd.DataFrame) -> str:
    """A specialized implementation for pandas DataFrames."""
    return f"A DataFrame with shape {data.shape} and columns: {list(data.columns)}"

@summarize.register(np.ndarray)
def _(data: np.ndarray) -> str:
    """A specialized implementation for NumPy arrays."""
    return f"A NumPy array with shape {data.shape}, dtype {data.dtype}, and mean {data.mean():.2f}"

print("Calling the generic function with different types:")
print(f"\n--- Summarizing an integer ---\n{summarize(123)}")
print(f"\n--- Summarizing a dictionary ---\n{summarize({'a': 1, 'b': [2, 3]})}")
df = pd.DataFrame({"price": [1, 2], "volume": [100, 200]})
print(f"\n--- Summarizing a DataFrame ---\n{summarize(df)}")
arr = rng.random((10, 3))
print(f"\n--- Summarizing a NumPy array ---\n{summarize(arr)}")

    Freezing Arguments with functools.partial¶

    functools.partial is a higher-order function that takes a function and a set of arguments, and returns a new, callable partial object that behaves like the original function but with those arguments pre-filled, or "frozen."

    Economic Application: This is extremely useful when working with numerical libraries. For instance, a numerical optimizer like scipy.optimize.minimize_scalar requires a function of a single variable, f(x). However, your objective function might be a more complex objective(x, param1, param2). You can use partial to create a new, one-argument function that is compatible with the optimizer: f = partial(objective, param1=value1, param2=value2).

    partial vs. lambda: While you could achieve a similar result with lambda x: objective(x, param1=value1, param2=value2), partial is generally superior. It is more explicit, often more readable, and the resulting object has useful attributes (.func, .args, .keywords) for introspection.

    def log_likelihood(mu: float, data: np.ndarray, sigma: float) -> float:
    """Calculates the *negative* log-likelihood for a normal distribution.
    We use the negative because optimizers typically minimize.
    """
    n = len(data)
    log_lik = -n / 2 * np.log(2 * np.pi * sigma**2) - (1 / (2 * sigma**2)) * np.sum(
        (data - mu) ** 2
    )
    return -log_lik  # Return negative for minimization

# Generate some sample data
true_mu, true_sigma = 5.0, 2.0
sample_data = rng.normal(loc=true_mu, scale=true_sigma, size=1000)

print(
    f"We want to find the Maximum Likelihood Estimate for 'mu', assuming sigma={true_sigma} is known."
)
print(
    "`minimize_scalar` requires a function of a single variable (mu). `partial` is perfect for this."
)

# Create a specialized version of the function where `data` and `sigma` are frozen.
objective_func = partial(log_likelihood, data=sample_data, sigma=true_sigma)

print("The partial object stores the original function and the 'frozen' arguments:")
print(f"  - Original function: {objective_func.func.__name__}")
print(
    "  - Frozen keyword arguments: {'data': 'np.ndarray(...)', 'sigma': objective_func.keywords['sigma']})"
)

# Now `objective_func` is a callable that only takes `mu`.
# We can pass it directly to the optimizer.
result = minimize_scalar(objective_func, bounds=(0, 10), method="bounded")

print("\n--- Optimization Results ---")
print(f"Optimizer success: {result.success}")
print(f"Estimated mu (MLE): {result.x:.4f}")
print(f"True mu:            {true_mu:.4f}")

    Aggregating Sequences with functools.reduce¶

    functools.reduce is a classic functional programming tool for producing a single result from a sequence. It applies a two-argument function cumulatively to the items of a sequence, from left to right, so as to reduce the sequence to a single value. For example, reduce(lambda x, y: x+y, [1, 2, 3, 4, 5]) calculates ((((1+2)+3)+4)+5).

    While Python's creator prefers a simple for loop for readability in most cases (especially for sums, where the built-in sum() is better), reduce can be an elegant tool for certain types of accumulation, such as calculating a cumulative product or applying a series of transformations.

    # Sequence of daily gross returns (1 + daily_return)
daily_gross_returns = [1.01, 0.99, 1.02, 1.005, 0.98]

# We want to calculate the total return over the period.
# The function to apply is lambda a, b: a * b (multiplication)
total_gross_return = reduce(operator.mul, daily_gross_returns)

print(f"Daily gross returns: {daily_gross_returns}")
print(f"Total gross return (product): {total_gross_return:.4f}")
print(f"Total net return: {(total_gross_return - 1):.2%}")

    Common Pitfalls in This Lecture

    • Late binding in closures. Closures capture variables, not values: [lambda: i for i in range(3)] yields three functions that all return 2. Bind early with a default argument (lambda i=i: i) or functools.partial.
    • Decorators erasing metadata. A decorator that returns a wrapper function replaces __name__ and the docstring with the wrapper's, breaking debugging and docs. Apply @functools.wraps(func) to the wrapper — always.

    Summary¶

    In this chapter, we have unlocked the full potential of Python functions. We have learned that:

    • Functions are Objects: Treating functions as data allows for powerful abstractions like higher-order functions and the Strategy Pattern.
    • Closures Capture State: Inner functions can carry their environment with them, enabling function factories.
    • Decorators Enhance Functions: We can wrap functions to add cross-cutting behavior like logging or caching (@lru_cache) cleanly.
    • Standard Library Tools: functools provides essential utilities like partial for freezing arguments and singledispatch for generic programming.

    These functional programming patterns are key to writing concise, modular, and performant code for economic modeling.

    Challenge Exercise: A Pluggable Event System for Simulations¶

    This exercise synthesizes multiple concepts to build a simple but powerful event-driven system, a common architecture for agent-based models or simulations.

    Objective: Create an EventSystem class that allows different parts of a program to register functions (handlers) that will be called when a specific event occurs.

    1. The EventSystem Class:

      • __init__(self): Initialize an empty dictionary, self._handlers, to store the event handlers. The keys will be event names (strings), and the values will be lists of functions (the handlers).
      • register(self, event_name: str) -> Callable: This method should be a decorator factory. It takes an event_name and returns a decorator. The decorator it returns should take a function (handler_func) and append it to the list for the correct event in self._handlers.
      • trigger(self, event_name: str, *args, **kwargs): This method takes an event name and any additional arguments. It should look up all registered handlers for that event and call each of them with the provided *args and **kwargs.

    2. Implementation and Demonstration: a. Create an instance: events = EventSystem(). b. Use the @events.register('simulation_start') decorator to register a function log_start_time(timestamp). c. Use the @events.register('simulation_end') decorator to register a function log_end_time(timestamp, status). d. Write a run_simulation function that: i. Calls events.trigger('simulation_start', timestamp=datetime.datetime.now()). ii. Prints a message like "... Running core logic ...". iii. Calls events.trigger('simulation_end', timestamp=datetime.datetime.now(), status='SUCCESS'). e. Run the simulation and show that your registered handlers were called automatically at the correct time.
